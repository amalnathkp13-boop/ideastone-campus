# Implementation coverage and remaining requirements

This branch delivers an integrated campus operations extension, **not the complete ImpresERP-equivalent definition of done**. The discovery inventory is intentionally broader than the implemented workflows. The requested complete ERP title must not be interpreted as certification that every advertised subfeature is finished.

## Delivered data and navigation

`ideastone_erp` adds 28 persistent models and extends faculty and stock receipts. The JSON navigation catalogue and XML actions are checked in. Each custom model has a real PostgreSQL-backed list, form and search interface with save/cancel, filters, sorting and native pagination. Numeric operational records also expose pivot/graph reports. All new records have company boundaries; deletion and updates respect approval state. No operational sample data is substituted for persistence.

Backend routes use Odoo's existing `/web#action=<action>` mechanism. The custom action identifiers below are prefixed with `ideastone_erp.action_`. The full navigation catalogue is `addons/ideastone_erp/models/navigation.json`. Standard actions retain their existing forms and business logic.

## Reference-derived additions

Old screenshots confirm fields for lesson units/hours/aids/reference URLs/CO levels; professional activities; qualification and service chronology; requests with date, department, purpose and evidence; visitor closure; catalog search; counseling; payroll history; and attendance status adjustments. These influenced the new records and retained native modules. The supplied staff HTML also informed personal/contact, employment, qualification, reporting and compliance sections.

All 117 old images were accessible and OCR extracted. [The reference register](erp-reference-register.csv) records the files and distinguishes contact-sheet overview from OCR-only review. OCR is imperfect, and some screenshots show the reference application's permission-denied page rather than its protected form. Hidden fields were not invented as discovered requirements. `Erp new ss` was listed in the parent folder but was not used because it is outside the specified reference priority.

## Assumptions and integrity

Manager approval is required for final financial, residence, circular, publication and development decisions. Purchase indents additionally require department and finance review; the same authorized manager can hold multiple roles until the college configures separate reviewers. Approved records are immutable except workflow-managed links, archive status and authorized payment evidence. Submitted/approved records cannot be deleted. Room allocation locks room/student records to serialize concurrent decisions, checks every date boundary, and rejects duplicate residences. Transport uses one active allocation per student per academic year. Attendance-device references and feedback keys are database-unique. File downloads require authenticated mapped identities and batch access. Portal identifiers never authorize access by themselves.

Placement eligibility uses the most recently entered result per subject rather than a university-specific weighted transcript. Payroll uses the employee work calendar/timezone, clips attendance to the payroll interval and stores a reviewed snapshot. Paid leave is operator-classified and cannot exceed approved leave wholly contained in the period; leave spanning periods requires allocation before processing. Concession, academic weighting, regulatory GPA and statutory filing rules were not supplied, so the branch does not certify those workflows.

## Validation ledger

Ruff, Python compilation, XML syntax and Compose configuration were executed successfully. The first real install identified and corrected a missing Odoo group XML ID, a view company-domain restriction and a wrong import. Workflow tests found and corrected feedback precomputation and an implicit calendar assumption. HTTP checks found and corrected Python/QWeb boolean syntax. A disposable-container filestore problem was corrected by using a shared QA data volume and a fresh database.

The final executed test counts, HTTP results and remote CI result are recorded in the PR description. A test declared in code is not proof of success; failed intermediate runs are not counted as passing. Model/action validation does not establish that every advertised business process is implemented. Browser preview URLs were blocked, so interactive desktop/mobile and visual-reference comparison remain unverified. No screenshots are claimed as completed UI evidence. Existing Keycloak/OpenOlat live integration, payment, messaging, biometric hardware and financial posting were not exercised against college accounts.
